Final review of worktoy before the 1.1.0 release candidate.

This session reads every package of worktoy and reports what would
embarrass a release candidate: a promise the code does not keep, an
error path that misleads, code that is dead, or a line that breaks the
rules the project holds itself to. It changes nothing. I decide what
gets fixed, after reading the report.

Begin by reading research_rules.txt, currently at
archive/research_rules.txt. It holds the settled and the deferred
items: the decisions already made about worktoy. Reading it spoils
nothing. One override: its Scope lines say the leaf packages are out
of scope and that a failing leaf test is removed rather than fixed.
That was true during the core refurbishment. Since 2026-11-05 every
leaf has been reworked and tested to the same standard, and the
candidate ships all of them, so this review covers every package
alike. Read docstring_format.md, beside it, for the docstring voice.

Avoid spoilers. Until the report is complete, do not open the memory
files listed in MEMORY.md, the hand-offs, anything under archive/
other than the two files named above, or anything under
bin/dev_tooling/review/archive/. Work from the code, the tests and
research_rules.txt alone.

To show that you understand the instructions, print a description of
how you understand them before you begin.

The report
----------

Create bin/dev_tooling/review/final_review_rc_[TIMESTAMP].md before
reading the first source file. This is the only file the session
creates inside the repository. Append to it as you go: the first entry
is written before you move deeper into the first package, and every
package ends with its entry in the ledger below. A session that dies
leaves a report that is complete up to the package it was in.

The report begins with a summary, filled in last: the count of
findings per classification, and whether the ledger is complete.

The ledger: for every package, the list of files read in full. The
review of a package is complete only when every file under
src/worktoy/<package>/ is in its ledger. Count them with find.

Probes run inline (python -c) or from files in the session's
scratchpad. Nothing else is written inside the repository.

What to review, package by package
----------------------------------

Order: utilities, waitaminute, core, dispatch, desc, mcls, keenum,
ezdata, lorem_ipsum, work_test. Read every file of a package in full
before writing about it.

1. Promises against behaviour. The docs of worktoy are the source
   files themselves, rendered verbatim, so every docstring is a
   promise. So are the member lists of the __init__ docstrings, the
   prose of README.md, and every entry of the [1.1.0] section of
   changelog.md that touches the package. Each claim that a few lines
   of code can check gets a probe, run for real. A claim the code does
   not keep is a finding. Do not decide the direction of the fix:
   present the wording change and the code change as labelled options.

2. Error paths. For every raise in the package: the message reads as
   plain language and names the right things (the owner-dotted name of
   a descriptor, the class, the value); the exception's __slots__ hold
   what the message shows; the type is worktoy's own where worktoy has
   one for the case. A message that would send a builder to the wrong
   place is a finding.

3. Dead private code. A private name (leading underscore, not
   exported) that nothing calls; a file no __init__ imports; a branch
   no input can reach. Coverage is 100 percent, so "no test reaches it"
   is not the measure; "no input can reach it" is. A public facility is
   never judged by whether worktoy itself uses it.

4. The floor. Python 3.7 is the floor and the gates verify the syntax,
   so do not re-run them. Check what the gates cannot: a stdlib name or
   signature that first appeared after 3.7, reached only on a path the
   3.7 run skips; a typing name imported at run time rather than under
   TYPE_CHECKING; an assumption that holds only on newer versions.

5. Consistency with the project's own rules. Sibling imports go
   through the package (from . import X). Private dunders are __x__,
   never __x. No regular expressions (the camelCase splitter in
   core/_object.py is the accepted exception). Files are opened with
   an explicit handle, the work in else, the close guarded in finally.
   Every super() call is listed with what it resolves to. 'True if cond
   else False' on a bool return is deliberate. Small named helpers are
   deliberate. Branches are explicit, never dict.get(key, default).
   Public names say what they do, not a related property. User-facing
   strings use plain words.

6. The mechanical sweep, one block in the report, with the commands:

     awk 'length > 77 {print FILENAME": "FNR}' src/worktoy/*/*.py \
       src/worktoy/*/*/*.py tests/*/*.py
     grep -rn $'\xe2\x80\x94' src tests README.md CONTRIBUTING.md \
       changelog.md
     grep -rn '``' src                      # double backticks
     grep -rLn 'Apache-2.0 license' --include='*.py' src tests
     grep -rn '# pragma' src tests          # each one justified?
     grep -rn '^ *pass$' src tests          # a body that never runs
                                            # carries a docstring
     find src tests -name __pycache__       # must be empty

Judgement
---------

Before writing any entry, check it against the settled items of
research_rules.txt. They are decisions already made. Do not raise
them, and do not offer options that remove, narrow or replace them.
Mention one only if the code no longer matches the decision. Deferred
items are known; do not raise them as new.

- Only behaviour inside the documented contract counts as a defect.
- Before raising a problem, ask whether a project built on worktoy
  would hit it.
- Judge a mechanism by what it lets a project do, never by how many
  places in src use it. "Nothing in src uses it" is not a reason to
  remove or change anything.
- A mistake Python already fails on fails the same way through
  worktoy, by design. Before rating anything above No Concern, write
  the plain-Python twin of the probe and run it; if Python fails the
  same way, the entry is No Concern and says so.
- Third-party code breaking Python's own contracts is not worktoy's
  problem; no guard is proposed for it.
- A refusal of something that does not exist, or a failure that
  follows literally from what a line asked for, is expected.
- Never propose documenting or testing a usage the library has not
  promised. A finding names a mismatch; it adds no promise.
- A gate is exact or it refuses; only numeric widening is allowed.
  FastBox is strict by design. Thread and task safety is deferred as a
  whole. The wording of an exception the interpreter composes is not
  worktoy's to keep.
- When worktoy needs ordinary attribute lookup it uses
  type.__getattribute__ on classes and object.__getattribute__ on
  instances, so no __getattr__ can answer. getattr used for this may be
  flagged. Plain reads of what every class has (__dict__, __mro__,
  __name__) are fine.
- A simplification must keep every capability. For any proposal that
  changes behaviour, show a table of what is kept, changed and dropped.
- "Less library code", "more explicit" or "plain Python" does not make
  a proposal better. Better means less for a project to write, fewer
  ways to get it wrong, and at least as much capability.

Entries
-------

Every entry begins with one of:

- No Concern
- Cosmetic
- Minor
- Major
- Critical

For this review, Critical and Major block the candidate; Minor and
Cosmetic are fixed before 1.1.0 or later, as I decide. A review where
nothing rises above No Concern is an acceptable result. Do not raise
items to fill the list, and do not hold back an item because the code
was called clean before.

Then, in this order: a one-line title; the location as path:line, with
the lines themselves quoted beside the explanation, never one without
the other; the promise quoted, when the entry is a mismatch (the
docstring, changelog or README text); the probe as you ran it, with
its real output, on worktoy_env (3.15) and, where versions differ, on
the base_3_x interpreters; what it touches; the recommendation, with
options labelled when there is more than one.

Operating rules
---------------

- Python: ~/miniforge3/envs/worktoy_env/bin/python for everything
  measured; ~/miniforge3/envs/base_3_7 to base_3_14 only to show a
  version difference. Always PYTHONDONTWRITEBYTECODE=1 and -B. No
  __pycache__ may appear under src or tests.
- Do not modify src, tests, docs, the workflows, the version files or
  the changelog. The report is the deliverable.
- Do not run git. Do not spawn sub-agents. No em-dash anywhere, the
  report included.
- Already verified tonight, do not redo: the wheel and sdist on PyPI
  match src; the suite passes against the wheel on 3.15 and 3.7; the
  rc coverage command holds at 100 percent; warnings as errors are
  clean on all nine interpreters; the README code blocks run; every
  package was swept with cosmic-ray.
